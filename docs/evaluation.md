# Eval DayOut

Состояние на 29 октября 2026 года: набор и runner подготовлены. Полный живой Eval
Alice Flash после исправлений **не выполнен**. Процент качества пока не измерен.
Успех pytest или искусственного сценария не означает успех реальной рекомендации.
Выполнены небольшие разработческие пилоты: они выявили ошибки формата плана,
обработки пустого результата и лишних ограничений при неизвестных ценах.
Их отчёты сохранены отдельно и не заменяют итоговую часть `holdout`.
В последнем пилоте завершились два сценария / три хода: новый поиск бань после
кафе с бюджетом 4000 ₽ на двоих и отдельная погода. 9 запросов LLM, 18 425 входных
и 813 выходных токенов. Ручные оценки оставлены `pending`: техническое завершение
не равно качеству. После него добавлен локальный запрет сочетать гарантию бюджета
с признанием неизвестных цен и уточнён просмотр фактически исполненных аргументов.
Эти последние изменения проверены локально; платного повтора после них нет.

## Что проверяем

В `eval/cases.json` находятся 30 живых сценариев — 37 пользовательских ходов.
20 сценариев / 24 хода отведены под настройку (`development`),
10 / 13 — под итоговую проверку (`holdout`). Это заранее выделенная часть того же
авторского набора, а не независимая внешняя экспертиза. После начала итогового
прогона по ней нельзя подбирать инструкции и одновременно считать её независимой.

| Область | Что считается корректным |
| --- | --- |
| Места | Соответствие цели, категории и географии; объяснение выбора по данным MCP |
| Бюджет | Исходная сумма, число людей и единица стоимости сохранены; неподтверждённые цены не выдаются за проверенные |
| Диалог | Смена кафе на бани вызывает новый поиск; новый бюджет заменяет прежний; отменённый бюджет не возвращается |
| Источники | Использованы возвращённые ссылки; общий вопрос не получает старый каталог мест |
| Погода | `lookup_weather`: текущая, суточная и почасовая; правильная дата и место; успешные данные для положительного кейса |
| Маршрут | `compute_routes`, пеший режим, правильные начало/конец; минуты не выдуманы |
| Идентификация | `resolve_names` и `resolve_maps_urls`; честная обработка неподдерживаемой ссылки |
| Сочетания | Прогулка + кафе + погода + маршрут в одном запросе |
| Нехватка данных | Один критичный вопрос либо честная неизвестность; отсутствие данных не заменяется выдумкой |

Отдельно четыре **искусственных** сценария: пустая выдача, обрыв соединения,
отказ доступа и HTTP 429. Они используют запрограммированные ответы и не обращаются
к сети. Текущие четыре сценария проверяют общий транспорт через сохранённый адаптер
Groq; семантические правила Яндекса дополнительно проверяются в pytest.

## Что делает runner

Живые сценарии проходят через тот же `web_backend.run_action`, что Streamlit.
Это проверка локального веб-адаптера, не автоматический тест публичного браузера
или доступности Streamlit Cloud. У каждого сценария новый диалог; внутри него
все ходы используют одну память. Автоповтор не заменяет неудачную первую попытку.

Автоматически проверяются завершение ходов, нужные/запрещённые инструменты,
успех обязательных вызовов, ошибки аргументов, отдельные фразы, источники последнего
ответа. Эти признаки не доказывают релевантность, правильную географию, честность
описаний и соответствие суммы единице цены. Их оценивает человек по ответу **и
исходным данным MCP**, увиденным во время прогона.

Критерии: `relevance` — цель и категория; `constraints` — район, время, бюджет;
`grounding` — утверждения подтверждены; `honesty` — неизвестность раскрыта;
`tool_choice` — нужные действия без лишних; `dialogue` — условия сохранены;
`clarification` — уместный вопрос; `controlled_behavior` — обработка сбоя.
Для каждого назначенного критерия: `pass`, `fail` или `pending`. Сценарий успешен,
только если пройдены все автоматические проверки и все ручные критерии.

В отчёте отдельно считаются отказы сети/квот/доступа/сервиса и ошибки качества.
Отказ сервиса исключён из знаменателя качества модели, но остаётся неуспехом
сквозной системы (`live_end_to_end_pass_rate`). Прерванные лимитом сценарии считаются
`stopped`. Пока есть неразмеченные пригодные ответы, процент качества равен `null`.
Всегда показывайте число попыток, инфраструктурных отказов и остановок рядом с долей.

Отчёт содержит версии кода/набора (SHA-256), фактического провайдера и модель,
дату визита, время, вызовы, usage, статусы инструментов и оценки. В JSON не сохраняются
ответы, названия мест, адреса, Place ID, ссылки и содержимое Maps.
`--inspect` показывает доказательства только в терминале. Не перенаправляйте его
вывод в постоянный лог; в комментариях CSV описывайте тип ошибки без копирования Maps.

## Воспроизведение

Нужны установленные `requirements-dev.txt` и конфигурация по README.
Список сценариев не отправляет запросов:

```powershell
.\.venv\Scripts\python.exe eval_runner.py --list
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe eval_runner.py --mode simulated --output eval/results/offline-new.json
```

Начинайте живую проверку с небольшого пилота: смена категории с бюджетом и общий
вопрос после поиска. Это **платные** обращения к выбранной модели. Укажите новую
дату визита в пределах прогноза; пример ниже подходит для запуска 29 октября 2026.

```powershell
.\.venv\Scripts\python.exe eval_runner.py --mode live --case D04 --case D06 --visit-date 2026-10-30 --max-live-turns 4 --interactive-review --output eval/results/pilot-new.json
```

По умолчанию лимит — всего **5 пользовательских ходов за запуск**, а не пять
запросов к LLM. Один ход включает планировщик, несколько вызовов модели/инструментов
и возможное ограниченное исправление. Его расход и время включены в измерения.
Пауза между ходами — 5 с для Яндекса, 65 с для Groq; её можно изменить `--interval`.

Runner принимает цены оператора через `--input-rub-per-1k` и `--output-rub-per-1k`.
Их нужно взять из своего актуального тарифа перед запуском; они не зашиты в код.
Формула: `(вход × цена входа + выход × цена выхода) / 1000`.
Без цен или при отсутствующем usage стоимость остаётся неизвестной.
`--max-estimated-rub` проверяется **между ходами**: один ход может превысить порог;
это не жёсткий денежный лимит аккаунта и не итоговый счёт с налогами/скидками.
429/401/403/402 останавливают пакет. Ctrl+C сохраняет законченные сценарии;
расход прерванного внутри хода запроса может не попасть в отчёт.

После исправлений по пилоту и части для настройки зафиксируйте код/набор.
Ориентир полного измерения — три повтора каждого сценария: 90 сценарных попыток,
111 пользовательских ходов. Явно увеличьте предохранительный лимит:

```powershell
# Платно: 20 сценариев × 3 повтора = 72 пользовательских хода
.\.venv\Scripts\python.exe eval_runner.py --mode live --split development --repeat 3 --max-live-turns 72 --visit-date 2026-10-30 --interactive-review --output eval/results/development-new.json

# Платно: 10 сценариев × 3 повтора = 39 ходов, после фиксации версии
.\.venv\Scripts\python.exe eval_runner.py --mode live --split holdout --repeat 3 --max-live-turns 39 --visit-date 2026-10-30 --interactive-review --output eval/results/holdout-new.json
```

Отчёт и соседний `.review.csv` не перезаписываются. Можно заполнить оценки в CSV
и пересчитать агрегаты без новых API-запросов:

```powershell
.\.venv\Scripts\python.exe eval_runner.py --summarize eval/results/pilot-new.json --review eval/results/pilot-new.review.csv
```

Это печатает пересчитанные агрегаты; исходный JSON не меняется. Если доказательства
не были просмотрены при запуске, ставьте `pending`, а не угадывайте оценку по
счётчику инструментов. Для отчёта защиты нужны доля завершений и сквозного успеха,
медиана/p95 времени, токены/стоимость, отдельные результаты по инструментам
и 3–5 разборов ошибок. Не выдавайте одну успешную попытку за устойчивость.

## Исходная версия и ограничения исправлений

В `eval/baseline.json` записан Git-коммит `4ecc733…` до исправлений.
Это сохранённый код, **не измеренный результат**. Живой Eval исходной версии Alice
Flash не проведён, поэтому улучшение в процентах пока утверждать нельзя.
Для сравнения потребуется запуск прежнего кода через тот же набор и сопоставимый
runner, с одинаковыми условиями. Наблюдавшиеся раньше сбои Groq не заменяют baseline
Яндекса. Смена модели/цены/набора должна быть видна в отчёте.

Новые правила Яндекса используют отдельный LLM-план запроса. Python сохраняет
неизменённый бюджет и добавляет условия в фактический поиск; при новом поисковом
намерении требует вызов инструмента. План сам может ошибиться в классификации.
Поиск цен и проверка числового бюджета не доказывают доступность услуги на нужное
число людей. Если цены отсутствуют, агент должен раскрыть неизвестность.
Одна попытка расширения пустого поиска и соблюдение границ района всё ещё требуют
семантической ручной оценки. У Groq новая стадия планирования пока отключена.

Для плана используется [структурированный вывод Яндекса](https://aistudio.yandex.ru/ru/docs/ai-studio/operations/generation/completions-structured)
в отдельном запросе без `tools`. Проверенная совместимость: `uniqueItems` не
поддерживается сервером в response_format; это правило сохранено в локальной
валидации. Пробелы вокруг Markdown-блока также допускаются разборщиком.
Начальный запрос поиска уже содержит просьбу о ценах и единицах. Неизвестная
цена допускает честный итог без обязательного дополнительного запроса.

Maps может вернуть `isError=false` с пустыми `{}` в обеих частях ответа: для
search_places это нормализуется в успешную пустую выдачу. Это не HTTP 429 и не
ошибка доступа. Само отсутствие результата не доказывает отсутствие места.

Прямая проверка `lookup_weather` 29 октября вернула успешный структурированный
прогноз для Москвы на 30 октября: `isError=false`. LLM не вызывалась, прогноз на
диск не сохранялся. Это проверка одного инструмента с текущим ключом, не успешный
погодный сценарий агента и не объяснение старой ошибки без её аргументов.
В сравнении того же запроса с текущим ключом добавление `languageCode=ru` и `en`
привело к `isError=true` с отказом доступа; без необязательного languageCode
запрос вновь прошёл. В агенте поле исключается из погоды, локализацию выполняет
LLM. Это наблюдение конкретной интеграции, а не утверждение о запрете русского
языка в Weather API вообще. Полную причину ограничения со стороны Google
сравнение не устанавливает.
