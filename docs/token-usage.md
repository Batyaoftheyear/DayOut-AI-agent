# Сокращение расхода токенов

Дата проверки: 27 октября 2026 года. Провайдер и модель не менялись,
платный тариф и кэширование не подключались. Новых зависимостей нет.

## Изменения

1. Системные инструкции сокращены; особенности погодного запроса и маршрута
   перенесены в короткие описания соответствующих инструментов. Все пять
   инструментов остаются доступны для выбора LLM. Реальные схемы используются
   для проверки; удаляются аннотации, но сохраняются правила, имена полей и enum.
2. В следующих ходах не передаётся протокол старых tool_calls с их ID и аргументами.
   Передаются два последних пользовательских/ассистентских обмена и данные
   последнего из этих ходов с результатами инструментов, отдельным блоком данных.
   Если старые данные уже недоступны, для подтверждения фактов нужен новый поиск.
3. Исходные пользовательские запросы сохраняются без LLM-пересказа в порядке
   поступления, чтобы бюджет, район и запреты не исчезали через два хода.
   Старые запросы объединяются в компактный блок. При суммарных 12 000 символов
   новый ход отклоняется с предложением /reset; условия не удаляются молча.
4. Возвращённые URL хранятся в памяти приложения. В контексте они заменяются
   метками [S1], [S2]. Перед показом ответа приложение подставляет точные исходные
   URL. В аргументах инструментов метки тоже разворачиваются до MCP-вызова.
   Неизвестные метки и неподтверждённые ссылки блокируют ответ. Привязка summary
   к places, Place ID и метаданные источников сохраняются.
5. Если схема поиска содержит pageSize/page_size и LLM не указала его явно,
   приложение запрашивает 3 места. Явное количество не переопределяется.
6. Лимит ответа снижен с 2500 до 1600 токенов; текущая инструкция просит до 150 слов.
   Это верхняя граница, а не обещание экономии ровно на 900 токенов. Обрезанный
   ответ остаётся ошибкой, а не незаметно урезанным успешным результатом.
7. Ожидание квоты использует последние заголовки Groq. После первых успешных
   ответов оценка входа калибруется по prompt_tokens и размеру запроса; это всё ещё
   оценка с запасом, а не точный токенизатор. HTTP 429 остаётся возможен.
8. Обычный поиск мест без даты должен начинаться с search_places. Погода нужна
   по просьбе пользователя или для уличного плана на конкретный день. Поиск заведения
   в помещении при условии «холодно» не требует дополнительного прогноза.
   Это инструкция модели, а не запрет инструмента на уровне Python.
9. При ошибке метки/URL выполняется одна попытка исправления ответа с повторной
   проверкой, вместо требования повторить весь запрос вручную. Эта генерация
   расходует токены и учитывается в usage; она не гарантирует успех.
   Этот же общий лимит распространяется на проверку отдельных неподтверждённых
   утверждений о часах/пути и обещаний фоновой работы.
10. После сбоя обращения к Groq незавершённый ход можно явно продолжить через /retry
    в течение 5 минут, используя уже полученные результаты MCP. Состояние хранится
    в памяти процесса. Новая генерация по-прежнему передаёт контекст и расходует
    токены; модель может запросить дополнительные данные. Новый вопрос или /reset
    удаляет временный ход; перезапуск теряет его, просроченные данные не используются.
11. Ожидание квоты ограничено суммарными 45 секундами за попытку обработки.
    Превышающий бюджет запрос не отправляется, состояние сохраняется для /retry.
    При таймауте на границе LLM и HTTP 429 результаты тоже сохраняются. Частичный
    вывод содержит только названия/ссылки из метаданных; он не является готовым подбором.
12. Язык поиска по умолчанию ru, если поле языка поддерживается реальной схемой;
    явный язык не заменяется. Из search_places удалены ненужные directionsUrl,
    сохранены ссылки места и атрибуция. Ответы compute_routes не менялись.

## Измерения

На ранее полученных реальных схемах MCP постоянные инструкции и определения
инструментов уменьшились с 6903 до 5225 символов: на 24,3%. Это сравнение символов,
не измерение токенов и не сравнение полной стоимости диалогов.

В синтетическом примере с повторяющимся URL JSON метаданных источника уменьшился
с 356 до 134 символов. Настоящие данные Maps для бенчмарка в репозиторий не копировались.

Реальный обезличенный технический тест: поиск одного публичного музея и повтор
его названия/источника без нового поиска. Результаты из usage Groq:

| Ход | Обращения LLM | MCP-вызовы | Входные токены, сумма | Выходные токены, сумма | Время |
|---|---:|---:|---:|---:|---:|
| Поиск | 2 | 1 | 4517 | 66 | 2,4 с |
| Уточнение | 1 | 0 | 2378 | 13 | 0,6 с |

Ожидания квоты в этом прогоне не было. До оптимизации сопоставимые счётчики usage
не записывались, поэтому заявлять точный процент снижения токенов нельзя.
Задержки зависят от нагрузки, внешних API, текста, числа поисков и квот аккаунта.
Этот короткий прогон не заменяет Eval качества и не гарантирует скорость полного плана.

После уточнения погодной инструкции отдельный обезличенный технический поиск
одного кафе с верандой: 1 MCP-вызов (search_places), 2 обращения LLM, 5391 входной
и 94 выходных токена, 3,7 с. Погода не вызывалась, HTTP 400 и ожидания квоты не было.
Это другой запрос, поэтому он не доказывает процент экономии относительно теста
музея и не устанавливает причину прошлого HTTP 400. Даже один поиск может занять
заметную часть бесплатного токенового окна.

После исправления источников и продолжения хода: отдельный реальный технический
поиск одного публичного музея — 1 MCP-вызов, 2 обращения LLM, 4841 входной + 91
выходной токен, 2,5 с. В нём не потребовались исправление и восстановление;
эти ветки проверены локально с искусственными ответами и сетевыми ошибками.

После последних изменений живой технический поиск не начался из-за сетевой ошибки
при подключении к MCP. Новых замеров токенов/качества нет; предыдущие измерения
не относятся автоматически к новой версии инструкций.

## Как смотреть расход

```powershell
.\.venv\Scripts\python.exe dayout.py --usage
```

Флаг показывает prompt_tokens/completion_tokens каждого запроса. В конце хода
всегда показывается их сумма. Счётчики не включают предыдущие завершённые ходы и команду /check;
при продолжении включаются попытки текущего незавершённого хода до сбоя.
Повторная передача контекста учитывается в каждом новом запросе. Ошибочные попытки,
для которых usage не получен, могут иметь неизвестный расход; он не выдаётся за ноль.
При отсутствии части usage показывается неполный учёт. Метрики не записываются в файлы.

## Проверки и ограничения

128 технических тестов проходят. Проверены сохранение старых условий, атомарность
хода при сбое, соответствие меток источникам при нескольких поисках, подстановка
URL в аргументы MCP, pageSize без переопределения явного значения, реальные поля
JSON Schema и счётчики usage без подмены неизвестного расхода нулём.
Прежние проверки ошибок, секретов, лимитов и CLI продолжают проходить.
Добавлены проверки безопасной расшифровки известных кодов HTTP 400 и обработки
неизвестных кодов/неожиданных JSON-ответов без вывода содержимого ошибок провайдера.
Также проверены однократное исправление источников, продолжение после обрыва Groq
с корректным протоколом tool_calls и сохранением лимитов, исключение /check из usage,
сброс временного хода новым вопросом или /reset и отказ от просроченных результатов.
Проверены ограничение общего ожидания, отсутствие отправки при исчерпанном бюджете,
ручное продолжение после таймаута LLM/HTTP 429, язык поиска, удаление лишних ссылок,
однократное исправление обещаний проверки и отдельных утверждений о часах/пути.

Остаётся проверить на наборе пользовательских сценариев: качество рекомендаций,
работу длинного диалога, достаточность 3 результатов, качество кратких ответов,
географическую точность, погоду и маршруты. Валидация источников не доказывает
правильность всех утверждений модели.
